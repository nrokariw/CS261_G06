## 1. บทบาทผู้ใช้งานและเงื่อนไขก่อนเริ่มทดสอบ (User Roles & Pre-conditions)

### 1.1 บทบาทผู้ใช้งานในการทดสอบ (User Roles)

| รหัสบทบาท | บทบาท (Role) | คำอธิบายหน้าที่ในการทดสอบ | บัญชีตัวอย่าง / แหล่งอ้างอิง |
| :--- | :--- | :--- | :--- |
| **Role A** | **ผู้ให้ยืม (Lender / Item Owner)** | เจ้าของประกาศสิ่งของ ผู้ส่งมอบสิ่งของ บันทึกหลักฐานการส่งมอบ/รับคืน และเรียกดูประวัติหลักฐาน | Account A (`6809000001` — Ploy S. ในโหมด Demo หรือบัญชี TU จริง) |
| **Role B** | **ผู้ยืม (Borrower)** | ผู้ส่งคำขอยืมสิ่งของ คู่กรณีในรายการยืม-คืน และผู้เรียกดูหลักฐานการยืม-คืนของรายการตนเอง | Account B (`6809000002` — Boom N. ในโหมด Demo หรือบัญชี TU จริง) |
| **Role C** | **บุคคลภายนอก (Third-Party / Non-Participant)** | ผู้ใช้ที่เข้าสู่ระบบแล้ว **แต่ไม่ใช่** ทั้งผู้ให้ยืมและผู้ยืมในรายการนั้น (ใช้ทดสอบการป้องกันสิทธิ์เข้าถึง) | Account C (`6809000003` — Somchai K.) |
| **Role D** | **ผู้ใช้งาน TU Account (Student / Staff)** | ผู้ใช้งานที่มีบัญชี TU Active Directory ทั้งบทบาทนักศึกษา (`STUDENT`) และบุคลากร (`STAFF`) | บัญชี TU จริง หรือบัญชีจำลองเชื่อมต่อ TU REST API (เฉพาะ `US-09`) |

### 1.2 เงื่อนไขสภาพแวดล้อมก่อนเริ่มทดสอบ (Global Pre-conditions)

1. **ระบบพร้อมใช้งานครบทุกบริการ:** รันระบบผ่าน Docker (`make all`) หรือบริการ Frontend (`http://localhost:3000`), Backend (`http://localhost:8080`) และฐานข้อมูล MSSQL เชื่อมต่อกันสมบูรณ์ (`healthy`)
2. **การตั้งค่า TU API (สำหรับ `US-09`):** ตั้งค่า `TU_API_BASE_URL`, `TU_API_VERIFY_PATH`, และ `TU_API_TOKEN` ในไฟล์ `.env` ถูกต้อง และบริการ TU REST API ของมหาวิทยาลัยธรรมศาสตร์ตอบสนองได้ตามปกติ
3. **ข้อมูลตั้งต้นสำหรับการทดสอบ `US-06` ถึง `US-08`:**
   - **Role A (ผู้ให้ยืม)** สร้างประกาศสิ่งของไว้แล้วอย่างน้อย 1 รายการ (สถานะเริ่มต้น `Available`)
   - **Role B (ผู้ยืม)** ส่งคำขอยืมสิ่งของดังกล่าว และ **Role A** กดอนุมัติคำขอแล้ว ทำให้รายการคำขออยู่ในสถานะ `Accepted`
   - เตรียมไฟล์สำหรับทดสอบไว้ล่วงหน้า:
     - ไฟล์รูปภาพที่ถูกต้อง (เช่น `.jpg`, `.png`, `.webp` ขนาดไม่เกิน 3 MB) สำหรับถ่าย/แนบหลักฐานส่งมอบและส่งคืน
     - ไฟล์ที่ไม่ใช่รูปภาพหรือไม่รองรับ (เช่น `.txt`, `.pdf`) สำหรับทดสอบกรณี Error / Validation

### 2.1 US-06: บันทึกหลักฐานการส่งมอบสิ่งของ

> อ้างอิงข้อกำหนด: [Sprint2.md](./Sprint2.md#us-06-บันทึกหลักฐานการส่งมอบสิ่งของ) | Sequence Diagram: [history.puml](./uml/history.puml)

#### `UAT-US06-01`: บันทึกหลักฐานการส่งมอบ/รับของถูกต้องครบถ้วน
- **บทบาทผู้ทดสอบ:** Role A (ผู้ให้ยืม) หรือ Role B (ผู้ยืม) ที่เป็นคู่กรณีในรายการ
- **Pre-conditions:**
  1. ผู้ทดสอบเข้าสู่ระบบแล้วและเป็นคู่กรณีในรายการยืมเป้าหมาย
  2. รายการคำขอยืมมีสถานะ `Accepted` (ยังไม่มีการส่งมอบ)
  3. อยู่ที่หน้าจัดการคำขอ (`/requests` สำหรับผู้ให้ยืม หรือ `/my-borrows` สำหรับผู้ยืม)
- **Test Data:**
  - รูปภาพหลักฐานสภาพสิ่งของถูกต้อง (เช่น `handover_ok.jpg`, ขนาด < 3 MB)
  - หมายเหตุสภาพสิ่งของ: `"สภาพสมบูรณ์ อุปกรณ์ครบ พร้อมส่งมอบ"`
- **Test Steps:**
  1. เปิดรายการคำขอที่มีสถานะ `Accepted` แล้วกดปุ่ม **"ส่งมอบ / บันทึกหลักฐานการส่งมอบ"**
  2. แนบไฟล์รูปภาพ `handover_ok.jpg` และกรอกหมายเหตุสภาพสิ่งของ
  3. กดปุ่มยืนยันบันทึกหลักฐานการส่งมอบ
  4. รีเฟรชหน้าเว็บ (Reload) และตรวจสอบสถานะรายการยืม + สถานะสิ่งของ
- **Expected Results:**
  1. ระบบอัปโหลดรูปภาพและบันทึกข้อมูลสำเร็จ โดยแสดงข้อความยืนยันการส่งมอบเรียบร้อย
  2. สถานะของรายการยืม/ธุรกรรมอัปเดตเป็น `Borrowed` ทันที และยังคงแสดงผลถูกต้องหลังรีเฟรชหน้าเว็บ
  3. ใน Database มีข้อมูล Transaction เชื่อมโยงกับรูปภาพหลักฐาน สภาพสิ่งของ และ Timestamp การส่งมอบ
- **Post-conditions:** รายการยืมอยู่ในสถานะ `Borrowed` และมีหลักฐานช่วงส่งมอบบันทึกอยู่ในระบบ

#### `UAT-US06-02`: ส่งแบบฟอร์มบันทึกหลักฐานการส่งมอบโดยไม่แนบรูปภาพ หรือกรอกข้อมูลบังคับไม่ครบ
- **บทบาทผู้ทดสอบ:** Role A (ผู้ให้ยืม) หรือ Role B (ผู้ยืม)
- **Pre-conditions:**
  1. ผู้ทดสอบเข้าสู่ระบบแล้วและเป็นคู่กรณีในรายการยืมสถานะ `Accepted`
  2. เปิดหน้าต่าง/ฟอร์มบันทึกหลักฐานการส่งมอบสิ่งของ
- **Test Data:**
  - กรณี A: ไม่แนบไฟล์รูปภาพ แต่กรอกหมายเหตุ
  - กรณี B: แนบไฟล์ที่ไม่ใช่รูปภาพ/ไฟล์ผิดประเภท (เช่น `.txt`) หรือปล่อยช่องข้อมูลบังคับว่าง
- **Test Steps:**
  1. เปิดฟอร์มบันทึกหลักฐานการส่งมอบสำหรับรายการสถานะ `Accepted`
  2. ทดสอบกรณี A: ไม่เลือกไฟล์รูปภาพ แล้วกดปุ่มยืนยันการบันทึก
  3. ทดสอบกรณี B: เลือกไฟล์ไม่รองรับ หรือไม่กรอกข้อมูลบังคับให้ครบ แล้วกดปุ่มยืนยันการบันทึก
  4. ตรวจสอบสถานะรายการยืมและข้อมูลใน Database
- **Expected Results:**
  1. ระบบแจ้งเตือนข้อผิดพลาดบนหน้าจออย่างชัดเจน (เช่น กรุณาแนบรูปภาพสภาพสิ่งของ / กรอกข้อมูลบังคับให้ครบ / รูปแบบไฟล์ไม่ถูกต้อง)
  2. ระบบ **ไม่บันทึกข้อมูล** ลงใน Database และไม่อัปโหลดไฟล์ค้าง
  3. สถานะรายการยืมยังคงเป็น `Accepted` ตามเดิม (ไม่เปลี่ยนเป็น `Borrowed`)
- **Post-conditions:** ไม่มีการสร้าง Transaction หรือเปลี่ยนสถานะสิ่งของ

#### `UAT-US06-03`: ผู้ใช้ที่ไม่ได้เป็นคู่กรณีพยายามส่งข้อมูลบันทึกหลักฐานการส่งมอบ
- **บทบาทผู้ทดสอบ:** Role C (บุคคลภายนอก — Account C)
- **Pre-conditions:**
  1. มีรายการคำขอยืมของ Role A และ Role B ที่อยู่ในสถานะ `Accepted` (จดจำ `requestId` เป้าหมายไว้)
  2. ผู้ทดสอบล็อกอินด้วยบัญชี **Role C** ที่ไม่ได้เกี่ยวข้องกับรายการยืมนี้
- **Test Data:** `requestId` ของรายการยืมระหว่าง Role A และ Role B + ไฟล์รูปภาพทดสอบ
- **Test Steps:**
  1. เข้าสู่ระบบด้วยบัญชี Role C แล้วตรวจสอบหน้า `/requests` และ `/my-borrows` ว่าไม่แสดงรายการของ Role A–B
  2. ใช้เครื่องมือทดสอบ API (เช่น Postman / DevTools / `curl`) ส่งคำขอบันทึกหลักฐานการส่งมอบไปยัง API ของ `requestId` ดังกล่าวโดยใช้ Session/Token ของ Role C
- **Expected Results:**
  1. ในหน้า UI ปกติ Role C ไม่สามารถมองเห็นหรือกดดำเนินการกับรายการของผู้อื่นได้
  2. เมื่อยิง API โดยตรง ระบบปฏิเสธการดำเนินการด้วยสถานะ `403 Forbidden` (หรือ `401`/`403` ตามสิทธิ์)
  3. ข้อมูลรายการยืม สถานะคำขอ และฐานข้อมูลไม่มีการเปลี่ยนแปลง
- **Post-conditions:** สถานะรายการยืมของ Role A–B ยังคงเป็น `Accepted` ตามเดิม

### 2.2 US-07: บันทึกหลักฐานการส่งคืนสิ่งของ

> อ้างอิงข้อกำหนด: [Sprint2.md](./Sprint2.md#us-07-บันทึกหลักฐานการส่งคืนสิ่งของ) | Sequence Diagram: [historyofsubmis.puml](./uml/historyofsubmis.puml)

#### `UAT-US07-01`: บันทึกหลักฐานการส่งคืนสิ่งของถูกต้องครบถ้วน
- **บทบาทผู้ทดสอบ:** Role A (ผู้ให้ยืม) หรือ Role B (ผู้ยืม) ที่เป็นคู่กรณีในรายการ
- **Pre-conditions:**
  1. ผ่าน `UAT-US06-01` แล้ว โดยรายการยืมอยู่ในสถานะ `Borrowed`
  2. ผู้ทดสอบเข้าสู่ระบบในฐานะคู่กรณีของรายการดังกล่าว
- **Test Data:**
  - รูปภาพหลักฐานสภาพสิ่งของตอนคืน (เช่น `return_ok.jpg`, ขนาด < 3 MB)
  - หมายเหตุสภาพสิ่งของ: `"คืนของตรงเวลา สภาพปกติไม่มีความเสียหาย"`
- **Test Steps:**
  1. ไปที่หน้ารายการยืมสถานะ `Borrowed` (`/requests` หรือ `/my-borrows`)
  2. กดปุ่ม **"ส่งคืน / บันทึกหลักฐานการส่งคืน"**
  3. แนบไฟล์รูปภาพ `return_ok.jpg` และกรอกหมายเหตุสภาพสิ่งของตอนคืน
  4. กดยืนยันบันทึกหลักฐานการส่งคืน แล้วตรวจสอบรายการยืมและหน้ารายการสิ่งของทั้งหมด (`/`)
- **Expected Results:**
  1. ระบบบันทึกหลักฐานการส่งคืน (รูปภาพ, หมายเหตุ, Timestamp การส่งคืน) ผูกเข้ากับ Transaction ใน Database สำเร็จ
  2. สถานะของรายการยืมเปลี่ยนจาก `Borrowed` เป็น `Returned`
  3. สถานะของสิ่งของเปลี่ยนกลับเป็น `Available` และกลับมาแสดงให้ผู้ใช้อื่นขอยืมได้บนหน้าค้นหา/รายการหลัก (`/`)
- **Post-conditions:** รายการยืมอยู่ในสถานะ `Returned` และสิ่งของอยู่ในสถานะ `Available`

#### `UAT-US07-02`: ส่งแบบฟอร์มบันทึกหลักฐานการส่งคืนโดยไม่แนบรูปภาพ หรือกรอกข้อมูลบังคับไม่ครบ
- **บทบาทผู้ทดสอบ:** Role A (ผู้ให้ยืม) หรือ Role B (ผู้ยืม)
- **Pre-conditions:**
  1. มีรายการยืมอยู่ในสถานะ `Borrowed`
  2. ผู้ทดสอบเปิดฟอร์มบันทึกหลักฐานการส่งคืนสิ่งของ
- **Test Data:**
  - กรณี A: ไม่แนบรูปภาพหลักฐานการคืน
  - กรณี B: แนบไฟล์ผิดประเภท หรือเว้นว่างข้อมูลบังคับ
- **Test Steps:**
  1. เปิดฟอร์มบันทึกหลักฐานการส่งคืนสำหรับรายการสถานะ `Borrowed`
  2. ทดสอบไม่แนบรูปภาพ หรือกรอกข้อมูลบังคับไม่ครบ แล้วกดปุ่มยืนยัน
  3. ตรวจสอบการแจ้งเตือน สถานะรายการยืม และสถานะสิ่งของ
- **Expected Results:**
  1. ระบบแสดงข้อความแจ้งเตือนข้อผิดพลาดบนหน้าจอ
  2. ระบบไม่บันทึกรูปภาพหรือข้อมูลการคืนลง Database
  3. สถานะรายการยืมยังคงเป็น `Borrowed` และสถานะสิ่งของยังคงเป็น `Borrowed` (ยังไม่กลับเป็น `Available`)
- **Post-conditions:** ข้อมูล Transaction และสถานะรายการไม่เปลี่ยนแปลง

#### `UAT-US07-03`: ผู้ใช้ที่ไม่ได้เป็นคู่กรณีพยายามส่งข้อมูลบันทึกหลักฐานการส่งคืน
- **บทบาทผู้ทดสอบ:** Role C (บุคคลภายนอก — Account C)
- **Pre-conditions:**
  1. มีรายการยืมของ Role A และ Role B ที่อยู่ในสถานะ `Borrowed` (จดจำ `requestId` / `transactionId`)
  2. ผู้ทดสอบเข้าสู่ระบบด้วยบัญชี **Role C**
- **Test Data:** `requestId` / `transactionId` ของรายการยืมระหว่าง Role A และ Role B + ไฟล์รูปภาพทดสอบ
- **Test Steps:**
  1. เข้าสู่ระบบด้วยบัญชี Role C
  2. ตรวจสอบหน้าจัดการรายการยืม-คืนว่าไม่มีปุ่มดำเนินการของรายการดังกล่าว
  3. ยิง API บันทึกหลักฐานการส่งคืนไปยัง `requestId` / `transactionId` เป้าหมายโดยใช้ Session/Token ของ Role C
- **Expected Results:**
  1. ระบบปฏิเสธการดำเนินการทันที (`403 Forbidden`)
  2. สถานะรายการยืมยังคงเป็น `Borrowed` และไม่บันทึกหลักฐานการคืนจาก Role C ลง Database
- **Post-conditions:** รายการยืมของ Role A–B ไม่ได้รับผลกระทบ

### 2.3 US-08: เรียกดูประวัติและหลักฐานการยืม-คืนสิ่งของ

> อ้างอิงข้อกำหนด: [Sprint2.md](./Sprint2.md#us-08-เรียกดูประวัติและหลักฐานการยืม-คืนสิ่งของ) | Sequence Diagram: [history-send-bor-look.puml](./uml/history-send-bor-look.puml)

#### `UAT-US08-01`: ผู้ยืมหรือผู้ให้ยืมเปิดดูประวัติรายการยืมและหลักฐานทั้งสองช่วง
- **บทบาทผู้ทดสอบ:** Role A (ผู้ให้ยืม) และ Role B (ผู้ยืม)
- **Pre-conditions:**
  1. มีรายการยืมที่ผ่านการบันทึกหลักฐานครบทั้งช่วงส่งมอบ (`UAT-US06-01`) และช่วงส่งคืน (`UAT-US07-01`) แล้ว (สถานะ `Returned`)
- **Test Data:** รายการยืมที่เสร็จสิ้นระหว่าง Role A และ Role B
- **Test Steps:**
  1. เข้าสู่ระบบด้วยบัญชี **Role B (ผู้ยืม)** ไปที่หน้า `/my-borrows` แล้วเปิดดูรายละเอียดประวัติและหลักฐานของรายการดังกล่าว
  2. ตรวจสอบรูปภาพ หมายเหตุสภาพสิ่งของ และวัน-เวลา (Timestamp) ทั้งช่วงส่งมอบและช่วงส่งคืน
  3. ออกจากระบบแล้วเข้าสู่ระบบด้วยบัญชี **Role A (ผู้ให้ยืม)** ไปที่ `/requests` หรือประวัติของสิ่งของชิ้นนั้น แล้วเปิดดูรายละเอียดหลักฐานแบบเดียวกัน
- **Expected Results:**
  1. ทั้ง Role A และ Role B สามารถเปิดดูประวัติรายการยืมได้สำเร็จ (`200 OK`)
  2. หน้าจอแสดงรูปภาพหลักฐาน หมายเหตุสภาพสิ่งของ และ Timestamp ครบถ้วนทั้ง 2 ช่วง (ช่วงส่งมอบและช่วงส่งคืน) โดยรูปภาพโหลดแสดงผลได้จริงไม่แตก (ไม่เกิด 404/500)
- **Post-conditions:** แสดงข้อมูลประวัติและหลักฐานตรงตามข้อมูลใน Database ครบถ้วนตามสิทธิ์คู่กรณี

#### `UAT-US08-02`: บุคคลภายนอกพยายามเปิดดูหรือเข้าถึง URL/API ของหลักฐาน
- **บทบาทผู้ทดสอบ:** Role C (บุคคลภายนอก — Account C)
- **Pre-conditions:**
  1. มีรายการยืมที่มีหลักฐานบันทึกอยู่แล้วระหว่าง Role A และ Role B
  2. บันทึก URL หน้าเว็บ / API Endpoint ดูประวัติ/หลักฐาน (เช่น `GET /api/transactions/borrower/{borrowerId}` หรือ URL รูปภาพหลักฐาน) จาก Session ของคู่กรณีไว้สำหรับทดสอบ
- **Test Data:** Token/Cookie ของบัญชี Role C + URL/API Endpoint ของหลักฐานคู่กรณี Role A–B
- **Test Steps:**
  1. เข้าสู่ระบบด้วยบัญชี **Role C**
  2. ตรวจสอบเมนู/หน้ารายการในแอปพลิเคชันว่าไม่แสดงประวัติการยืม-คืนของ Role A และ Role B
  3. นำ URL หรือ API Endpoint ของประวัติ/หลักฐานของ Role A–B มาเรียกผ่านเบราว์เซอร์หรือเครื่องมือทดสอบ API โดยใช้สิทธิ์ของ Role C
- **Expected Results:**
  1. ระบบไม่อนุญาตและปฏิเสธการเข้าถึงด้วยสถานะ `403 Forbidden` (หรือปฏิเสธไม่ส่งคืนข้อมูลของผู้อื่น)
  2. Role C ไม่สามารถมองเห็นรูปภาพหลักฐาน หมายเหตุ หรือข้อมูลธุรกรรมของคู่กรณีอื่นได้
- **Post-conditions:** ข้อมูลและไฟล์หลักฐานของคู่กรณีได้รับการป้องกันการเข้าถึงจากบุคคลภายนอก

### 2.4 US-09: Login ด้วย TU Account

> อ้างอิงข้อกำหนด: [Sprint2.md](./Sprint2.md#us-09-login-ด้วย-tu-account) และ Test Issue `#101` | Sequence Diagram: [login.puml](./uml/login.puml)

#### `UAT-US09-01`: Login ด้วยข้อมูล TU Account ที่ถูกต้องสำเร็จตาม Role
- **บทบาทผู้ทดสอบ:** Role D — นักศึกษา (`STUDENT`) และบุคลากร (`STAFF`)
- **Pre-conditions:**
  1. มี TU Account ที่สถานะบัญชีปกติ (`Active` / `ปกติ` / `ปฏิบัติงาน` ตามข้อมูล TU REST API)
  2. ผู้ทดสอบอยู่ที่หน้า `/login` และยังไม่ได้เข้าสู่ระบบ
- **Test Data:**
  - ชุดที่ 1: Username และ Password ของบัญชีนักศึกษา TU (`type = "student"`)
  - ชุดที่ 2: Username และ Password ของบัญชีบุคลากร TU (`type = "employee"`)
- **Test Steps:**
  1. เปิดหน้า `/login` กรอก Username และ Password ของบัญชีนักศึกษา แล้วกด **"เข้าสู่ระบบ"**
  2. ตรวจสอบการเข้าสู่ระบบและออกจากระบบ
  3. กรอก Username และ Password ของบัญชีบุคลากร แล้วกด **"เข้าสู่ระบบ"**
- **Expected Results:**
  1. ระบบยืนยันตัวตนผ่าน TU REST API สำเร็จและเปลี่ยนหน้าเข้าสู่ระบบหลัก (`/`) พร้อมออก Session / JWT
  2. บัญชีนักศึกษาได้รับ Role `STUDENT` และบัญชีบุคลากรได้รับ Role `STAFF` ถูกต้องตามประเภทบัญชีจาก TU API
- **Post-conditions:** ผู้ใช้เข้าสู่ระบบสำเร็จและมี Session ที่ใช้งานได้

#### `UAT-US09-02`: Login ด้วยรหัสผ่านผิด หรือบัญชีสถานะไม่ปกติ
- **บทบาทผู้ทดสอบ:** Role D (ผู้ใช้ TU Account / ผู้กรอกข้อมูลผิด)
- **Pre-conditions:**
  1. ผู้ทดสอบอยู่ที่หน้า `/login`
  2. เตรียมทดสอบทั้งกรณีรหัสผ่านผิด, รูปแบบ Username ผิด, การกรอกผิดเกินโควตา (5 ครั้ง/10 นาที), และกรณีบัญชีสถานะไม่ปกติ (`403` เช่น พ้นสภาพ/พักการศึกษา/ลาออก ถ้ามีบัญชีทดสอบ)
- **Test Data:**
  - กรณี A: Username ถูกต้อง + Password ผิด
  - กรณี B: Username ผิดรูปแบบ (เช่น สั้นกว่า 3 ตัวอักษร หรือมีช่องว่าง)
  - กรณี C: กรอกรหัสผ่านผิดติดต่อกัน 5 ครั้ง แล้วลองครั้งที่ 6 จาก IP เดิม
- **Test Steps:**
  1. กรอก Username ที่ถูกต้องกับ Password ผิด แล้วกด **"เข้าสู่ระบบ"**
  2. กรอก Username ผิดรูปแบบ (เช่น `ab` หรือ `bad user`) แล้วกด **"เข้าสู่ระบบ"**
  3. ทดสอบกรอกรหัสผ่านผิดครบ 5 ครั้ง แล้วส่งคำขอครั้งที่ 6
- **Expected Results:**
  1. กรณี A (รหัสผิด): API คืน `401 Unauthorized` และหน้าจอแจ้งเตือนข้อความรหัสนักศึกษา/รหัสผ่านไม่ถูกต้อง ไม่อนุญาตให้เข้าสู่ระบบ
  2. กรณี B (รูปแบบผิด): หน้า Login แจ้งเตือนรูปแบบชื่อผู้ใช้ทันทีโดยไม่ยิงคำขอไปสิ้นเปลืองโควตา TU API
  3. กรณี C (ผิดเกิน 5 ครั้งใน 10 นาที): ระบบจำกัดอัตรา (Rate Limit) คืน `429 Too Many Requests` พร้อมข้อความแจ้งเตือนให้รอสักครู่
  4. กรณีบัญชีสถานะไม่ปกติ (หากทดสอบ): API คืน `403 Forbidden` และแจ้งเตือนสถานะบัญชีไม่พร้อมใช้งาน
- **Post-conditions:** ไม่ออก Session/Token ให้ผู้ใช้ และโควตา TU REST API ไม่ถูกผลาญซ้ำ

#### `UAT-US09-03`: Login ด้วยข้อมูลหลังการเปลี่ยนแปลงใดๆ ใน TU Account
- **บทบาทผู้ทดสอบ:** Role D (บัญชี TU ที่มีการเปลี่ยนแปลงข้อมูลโปรไฟล์ รหัสผ่าน หรือ Role)
- **Pre-conditions:**
  1. บัญชีทดสอบเคยล็อกอินเข้าสู่ระบบอย่างน้อย 1 ครั้งมาก่อนหน้านี้
  2. มีการเปลี่ยนแปลงข้อมูลใน TU Account (เช่น เปลี่ยนชื่อแสดงผล, คณะ/หน่วยงาน, สาขาวิชา, Role, หรือเปลี่ยนรหัสผ่านใหม่ — หากทดสอบ Cache ควรรอพ้นช่วง TTL 5 นาทีหลังล็อกอินครั้งก่อน)
- **Test Data:** Username และรหัสผ่านล่าสุด (ใหม่) ของ TU Account หลังการเปลี่ยนแปลง
- **Test Steps:**
  1. เปิดหน้า `/login` และกรอก Username กับ Password ปัจจุบัน (ค่าใหม่)
  2. กด **"เข้าสู่ระบบ"** และเปิดดูข้อมูลโปรไฟล์ผู้ใช้ในแถบด้านบน
  3. ตรวจสอบข้อมูลในตาราง `users` ของ Database
- **Expected Results:**
  1. สามารถเข้าสู่ระบบด้วยรหัสผ่านใหม่ได้สำเร็จ (`200 OK`)
  2. ระบบซิงก์ข้อมูลล่าสุดจาก TU REST API มาอัปเดตทับข้อมูลเดิม (`fullName`, `email`, `faculty`/`organization`, `department`, `role`) ทั้งบนหน้าจอและใน Database
- **Post-conditions:** ข้อมูลโปรไฟล์และ Role ในระบบตรงกับข้อมูลล่าสุดใน TU Account

#### `UAT-US09-04`: Login ด้วยข้อมูลก่อนการเปลี่ยนแปลง (รหัสผ่านเก่า) หลังจากเปลี่ยนรหัสผ่านใน TU Account แล้ว
- **บทบาทผู้ทดสอบ:** Role D (บัญชี TU ที่เปลี่ยนรหัสผ่านแล้ว)
- **Pre-conditions:**
  1. บัญชีเคยล็อกอินด้วยรหัสผ่านเก่าสำเร็จมาก่อน
  2. ผู้ใช้ได้เปลี่ยนรหัสผ่านบนระบบของมหาวิทยาลัย (TU Account) เป็นรหัสผ่านใหม่เรียบร้อยแล้ว (และพ้นช่วง Short-TTL Cache 5 นาทีหากเพิ่งล็อกอินด้วยรหัสเก่า)
- **Test Data:** Username เดิม + **รหัสผ่านเก่า** (ก่อนเปลี่ยน)
- **Test Steps:**
  1. เปิดหน้า `/login`
  2. กรอก Username เดิมร่วมกับ **รหัสผ่านเก่า** แล้วกด **"เข้าสู่ระบบ"**
- **Expected Results:**
  1. ระบบปฏิเสธการเข้าสู่ระบบ (`401 Unauthorized`) และแสดงข้อความแจ้งเตือนรหัสผ่านไม่ถูกต้อง (ต้องไม่ตกค้างหรือยอมให้ผ่านจาก `passwordHash` ใน Database)
- **Post-conditions:** ผู้ใช้ไม่สามารถเข้าสู่ระบบด้วยรหัสผ่านเก่าได้

#### `UAT-US09-05`: แสดงข้อมูลที่ผูกติดกับบัญชีอย่างถูกต้อง และจำกัดสิทธิ์ตาม Role
- **บทบาทผู้ทดสอบ:** Role D (`STUDENT` / `STAFF`) และผู้ใช้ที่ยังไม่ได้ Login (`Unauthenticated`)
- **Pre-conditions:**
  1. ผู้ทดสอบเข้าสู่ระบบสำเร็จจาก `UAT-US09-01`
- **Test Data:** บัญชี TU ที่เข้าสู่ระบบแล้ว (`STUDENT` / `STAFF`) vs ผู้ใช้งานที่ยังไม่เข้าสู่ระบบ
- **Test Steps:**
  1. หลังเข้าสู่ระบบสำเร็จ ให้คลิกเปิดเมนูโปรไฟล์ที่มุมขวาบนของแถบนำทาง (Profile Popover)
  2. ตรวจสอบการแสดงผลฟิลด์ `fullName`, `username`/`studentId`, ป้าย `role` (`นักศึกษาผู้ใช้งาน` / `บุคลากร`), `faculty` (หรือหน่วยงาน), และ `department`
  3. ตรวจสอบสิทธิ์การเข้าถึงหน้าและ API:
     - ลองเข้าหน้า Protected Routes (`/create`, `/my-listings`, `/requests`, `/my-borrows`) ขณะ **ยังไม่ Login** เทียบกับหลัง **Login แล้ว**
     - ลองทำรายการที่ผูกกับความเป็นเจ้าของ/คู่กรณี (เช่น แก้ไข/ลบประกาศของผู้อื่น หรืออนุมัติ/บันทึกหลักฐานของรายการผู้อื่น)
- **Expected Results:**
  1. Profile Popover แสดง `username`, `role`, `faculty`/`organization`, และ `department` ตรงตามบัญชีที่ล็อกอินเข้ามาทุกประการ
  2. ผู้ใช้ที่ยังไม่ Login ถูกส่งกลับไปหน้า `/login` และเรียก Protected API ไม่ได้ (`401 Unauthorized`)
  3. ผู้ใช้ที่ Login แล้วใช้งานบริการสร้างประกาศ ขอยืม และดูรายการตามสิทธิ์ของบัญชีตนเองได้ แต่ถูกปฏิเสธ (`403 Forbidden`) เมื่อพยายามเข้าถึง/แก้ไขรายการที่ไม่มีสิทธิ์หรือไม่ใช่คู่กรณี
- **Post-conditions:** การแสดงข้อมูลบัญชีและการบังคับใช้สิทธิ์ทำงานถูกต้องครบถ้วน
